# 보안 점검 보고서 (2026-08-06)

> **누가 읽는 문서인가**: 보안 전문가가 아니어도 읽을 수 있게 썼습니다.
> 전문 용어는 처음 나올 때 괄호로 풀어 씁니다.
> **점검 방법**: 국제 표준 점검표(OWASP Top 10 · OWASP ASVS) + 위협 모델링(STRIDE) + 암호 구현 기준(NIST) 4가지를
> 각각 독립된 조사로 수행하고 결과를 합쳤습니다. 주장은 **실제로 재현해 확인**했습니다(재현 성공/차단됨을 표기).

---

## 1. 한 장 요약

밥장부는 **기본기가 매우 좋은 앱입니다.** 외부에서 가져다 쓰는 코드가 하나도 없고(공급망 공격 불가),
서버는 실제로 직원 이름·금액을 갖고 있지 않으며, 손님이 만지는 잠금 화면은 96개 기능을 시험해도 전부 막혔습니다.

다만 **필드테스트(실제 가게 투입) 전에 반드시 고쳐야 할 것 6가지**가 나왔습니다.
그중 둘은 "남의 명단을 통째로 가져갈 수 있는" 경로이고, 하나는 **기관이 보낸 파일을 여는 정상 사용 흐름에서 터집니다.**

| 등급 | 개수 | 뜻 |
|---|---|---|
| 🔴 지금 고쳐야 함 | 6 | 실제 피해가 나는 경로. 대부분 수정은 몇 줄~반나절 |
| 🟡 파일럿 중 고치면 됨 | 12 | 위험하지만 조건이 붙거나 피해가 제한적 |
| 🟢 잘 되어 있음 | 13 | 유지할 강점 |

## 2. 🔴 지금 고쳐야 할 6가지

### ① 남의 가게를 먼저 등록해서 명단을 가로챌 수 있다
**쉬운 설명** — 가게를 등록할 때 "당신이 정말 그 가게 주인인지" 확인하지 않습니다. 선착순입니다.
가게 고유번호는 공공데이터에 공개돼 있어서 누구나 압니다.
**무슨 일이 생기나** — 나쁜 사람이 아직 등록 안 한 식당 이름으로 먼저 등록해 두면, 구청 담당자 화면에는
정상 가게처럼 보입니다. 담당자가 그 가게를 골라 명단을 보내면 **공무원 실명·부서·개인별 금액이 통째로 그 사람에게** 갑니다.
진짜 사장님은 나중에 등록하려다 "이미 등록됨" 오류만 보게 됩니다.
**고치는 법** — 등록할 때 서버가 공공데이터로 가게 이름·주소를 대조. (반나절)

### ② 기관이 보낸 엑셀 파일을 여는 것만으로 앱이 장악될 수 있다 ⚠️ 가장 현실적
**쉬운 설명** — 엑셀(CSV) 금액칸에 이상한 값이 있으면 "금액 오류: OOO" 하고 보여주는데,
그 OOO를 **글자가 아니라 명령으로 실행**해 버립니다.
**무슨 일이 생기나** — 사장님이 파일을 고르는 순간 실행됩니다. 승인 버튼도 필요 없습니다.
공격자는 가게의 **암호 열쇠(개인키)를 훔쳐** 이후 오는 모든 명단을 몰래 열어볼 수 있습니다.
**왜 제일 급한가** — ①③은 "속아서 이상한 파일을 받아야" 하지만, 이건 **정상 업무 흐름**입니다.
**고치는 법** — 오류 메시지를 글자로만 표시하도록 한 줄 수정. (5분)

### ③ 서명 그림을 통해서도 같은 장악이 가능하다
**쉬운 설명** — 직원 서명 이미지를 화면에 그릴 때 ②와 같은 실수가 3곳 있습니다.
**무슨 일이 생기나** — 조작된 백업 파일을 복원하면 이력 화면을 열 때마다 공격 코드가 실행되고, 역시 개인키가 털립니다.
더 나쁜 경우: **중계 서버가 해킹당하면** 서버가 스스로 조작된 백업을 만들어 가게 앱을 장악할 수 있습니다
(원래 "서버는 훔쳐볼 수 없다"가 이 서비스의 약속인데, 그게 깨집니다).
**고치는 법** — 3곳에 안전 처리 함수 추가 + 서명 형식 검사 강화. (10분)

### ④ 인터넷 주소만 알면 "누가 얼마를 보냈는지"를 아무나 볼 수 있다
**쉬운 설명** — 수신함 조회에 로그인이 필요 없습니다. 가게 번호만 넣으면 됩니다.
**무슨 일이 생기나** — 명단 내용(이름·금액)은 암호로 잠겨 있어 못 봅니다. 하지만
**"강남구청 총무과가 이 식당에 27명분 81만원을 보냈다"**는 사실은 전국 어느 가게든 수집할 수 있습니다.
2~3명짜리 작은 과에서는 총액÷인원으로 개인 금액이 사실상 드러납니다.
**고치는 법** — 이미 다른 기능(승인·백업)에 쓰고 있는 본인 확인 절차를 조회에도 적용. (1일)

### ⑤ 인증 메일 100통을 소진시켜 기관 담당자 전원을 못 들어오게 만들 수 있다
**쉬운 설명** — 인증번호 메일 발송에 아무 제한이 없습니다. 무료 요금제라 하루 100통이 한도입니다.
**무슨 일이 생기나** — 공격자가 2분이면 그날 100통을 다 써버립니다. 그러면 **그날 하루 종일 어떤 담당자도
로그인할 수 없어 명단 전송이 전면 중단**됩니다. 비용 0원으로 매일 반복 가능합니다.
**고치는 법** — 사람인지 확인하는 절차(Turnstile, 무료) + 서버가 하루 발송량을 스스로 세기. (반나절)

### ⑥ 브라우저 보안 장치(CSP 등)가 5개 사이트 전부 꺼져 있다
**쉬운 설명** — 웹 브라우저에는 "이 사이트는 여기 외에는 아무 데도 데이터를 못 보낸다" 같은
안전벨트가 있는데, 하나도 안 켜져 있습니다.
**무슨 일이 생기나** — ②③ 같은 사고가 났을 때 **피해를 막아줄 2차 방어선이 없습니다.**
또 다른 사이트가 우리 화면을 몰래 덮어씌워 승인 버튼을 누르게 하는 공격(클릭재킹)도 가능합니다.
**고치는 법** — 설정 파일 2개 추가 + Cloudflare 스위치 켜기. (2시간, 코드 수정 거의 없음)

## 3. 🟡 파일럿 중 고치면 되는 것 (요약)

| 항목 | 쉬운 설명 | 왜 급하지 않나 |
|---|---|---|
| 장부 위조 탐지 범위가 좁다 | 마지막 거래 삭제, "사용"을 "충전"으로 바꾸기, 서명 바꿔치기가 **탐지되지 않는다**(실제 실험으로 확인) | 기기를 만질 수 있는 사람만 가능. 다만 분쟁 시 "장부가 안전하다"는 주장은 약해짐 |
| "3중 검증"이 사실은 1중 | 무결성 검사가 같은 값을 두 번 계산해 비교하는 구조라 **항상 통과**한다 | 잘못을 만들진 않지만 **없는 안전감**을 준다 |
| PIN이 약하게 저장됨 | 4자리 비밀번호가 소금(salt) 없이 저장돼, 기기를 뜯으면 1초 만에 풀린다 | 기기 물리 확보가 전제 |
| 열쇠가 자물쇠 옆에 있다 | 전화번호를 푸는 열쇠가 암호문과 같은 서랍에 평문으로 있다 | 서버 유출에는 안전. 기기 침해에만 해당 |
| 담당자 웹 서버 주소를 바꿀 수 있다 | 공용 PC에서 앞사람이 주소를 바꿔 두면 다음 사람의 명단이 엉뚱한 곳으로 암호화된다 | 공용 PC 시나리오 한정 |
| 로그아웃 버튼이 없다 | 담당자가 자리를 뜰 때 세션을 끊을 방법이 없다(탭 닫으면 사라지긴 함) | 탭 닫기로 대체 가능 |
| 캐시에 암호문이 남는다 | 수신함 응답이 기기에 영구 저장된다 | 암호문이라 바로 읽히진 않음 |
| 이메일이 약하게 익명화됨 | 해시만 저장하지만 소금이 없어, DB가 유출되면 원래 주소를 복원할 수 있다 | DB 유출이 전제 |
| 재전송이 조용히 삼켜진다 | 지난달과 인원·금액이 같으면 8월 명단이 **전달되지 않는데 성공으로 보인다** | 보안보다 실사용 버그 |
| 개인정보처리방침 누락 3건 | 메일 발송 업체(미국) 위탁, 의견함 자유입력, 등록 가게 공개 게시가 방침에 없다 | 법적 리스크, 문구 수정으로 해결 |
| 리포 전체가 앱 주소로 공개 | `app.bapjangbu.com/server/...`로 서버 코드가 열린다 | 이미 공개 저장소라 새 노출은 아님 |
| 직원용 앱 복원 검증 부족 | 백업 파일로 개인 기록장에 코드 실행 가능 | 그 폰의 개인 기록만 영향 |

## 4. 🟢 잘 되어 있는 부분 (그대로 유지)

1. **외부 코드 0개** — 광고·추적기·CDN이 하나도 없습니다. 요즘 웹 사고의 상당수가 "남의 코드"에서 오는데 그 통로가 아예 없습니다.
2. **서버가 정말로 내용을 모릅니다** — 스키마 전체를 뒤져도 직원 이름·개인 금액·전화번호 컬럼이 없습니다.
3. **손님 잠금 화면이 견고합니다** — 96개 기능을 강제로 실행해 보고, 파일 넣기·키보드·뒤로가기까지 시도했지만 **전부 막혔고 장부는 1건도 바뀌지 않았습니다.**
4. **암호 방식이 교과서대로입니다** — 암호 종류·키 길이·난수 생성이 표준과 정확히 일치하고, 매번 새 값을 씁니다(흔한 재사용 실수 없음).
5. **본인 확인 절차가 잘 설계됐습니다** — 승인·해제·백업에 "그 기기만 풀 수 있는 문제"를 내는 방식이고, 한 번 쓰면 즉시 폐기됩니다.
6. **담당자 웹은 XSS 공격을 전부 막았습니다** — 악성 서버를 흉내 내 3종류 공격을 시도했지만 모두 차단됐습니다.
7. **CORS(다른 사이트의 무단 호출 차단)가 정석입니다** — 우회 시도 4종 전부 실패.
8. **보관 기간이 코드로 강제됩니다** — 명단 3일, 요약 30일, 동의 기록 180일이 자동 삭제됩니다.
9. **비밀번호 5회 실패 시 60초 잠금이 새로고침으로 안 풀립니다.**
10. **초기화할 때 서버 등록도 함께 해제**하고, 비밀번호 분실 복구 때는 **일부러 해제하지 않아** 가게 가로채기를 막습니다.
11. **관리자 토큰 비교가 시간차 공격에 안전**하고, 미설정 시 기능이 잠깁니다.
12. **비밀값(API 키 등)이 저장소에 하나도 없습니다**(과거 이력 포함 확인).
13. **적대적 검증 문화** — 지난 개발 과정에서 배포 전에 실제로 치명 결함 여러 건을 잡아낸 이력이 있습니다.

|---|---|---|---|
| 1 | ② CSV 오류 메시지 안전 처리 | 5분 | 정상 업무에서 터지는 유일한 경로 |
| 2 | ③ 서명 3곳 안전 처리 + 형식 검사 | 10분 | 같은 계열, 함께 처리 |

| 6 | ⑤ 메일 발송 보호 | 반나절 | 하루 만에 서비스 마비 가능 |

## 6. 이 점검의 한계 (정직하게)

- Cloudflare 대시보드 설정(WAF·속도 제한·HSTS)은 접근할 수 없어 **확인하지 못했습니다.** 이미 켜져 있다면 몇몇 위험도가 내려갑니다.
- 실제 공격은 하지 않았습니다(부하 시험·메일 폭탄·데이터 삭제 금지). 코드 분석과 **안전한 재현**으로만 확인했습니다.
- 직원용 앱은 별도 저장소라 이번에 처음 같은 기준으로 점검했습니다.
- 라이브 인증 메일 발송은 하루 한도를 소모하므로 **2건만** 확인했습니다.

## 7. 용어 풀이

| 용어 | 쉬운 뜻 |
|---|---|
| XSS | 화면에 글자로 보여야 할 것이 **명령으로 실행**되는 사고 |
| 개인키 | 암호를 푸는 열쇠. 이게 털리면 지금까지 받은 명단을 전부 열 수 있음 |
| CSP | "이 사이트는 정해진 곳 외에는 데이터를 못 보낸다"는 브라우저 안전벨트 |
| 해시 | 내용을 고정 길이 지문으로 바꾸는 계산. 되돌릴 수 없음 |
| 소금(salt) | 해시에 섞는 임의값. 없으면 미리 계산된 표로 순식간에 뚫림 |
| zero-knowledge | 서버가 내용을 모르는 구조 |
| STRIDE | 위장·변조·부인·유출·마비·권한상승 6가지로 위협을 훑는 표준 방법 |
| OWASP Top 10 | 웹 보안 사고 상위 10유형 국제 점검표 |
