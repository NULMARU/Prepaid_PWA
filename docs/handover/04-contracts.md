# 04 — 깨면 안 되는 계약

**API 스펙 전체는 `server/PROTOCOL.md`에 있다.** 이 문서는 그 중에서 *"조용히 깨지고, 깨진 줄도 모르는"* 항목만 추린 것이다. 각 항목에 **깨졌을 때 무슨 일이 벌어지는가**를 명시한다.

> 여기 있는 14개는 전부 실제로 깨졌거나(2건은 라이브 장애), 깨질 뻔한 것이다.
> C9~C14는 2026-09(beta.48)에 추가됐다 — 대부분 **"같은 돈이 장부에 두 번 들어가는 길"** 을 막는 계약이다.

## C1. `batch_hash` canonical — `name|dept|amount`

**계약**
```
canonical = items를 "name|dept|amount" 문자열로 만들어 정렬 후 "\n" join
batch_hash = SHA-256(canonical) 소문자 hex
```
세 곳이 **독립적으로 같은 산식**을 구현하고 있다:
- 담당자 웹 `agency-web/index.html` — `canonOf()` / `batchHash()`
- 음식점 앱 `index.html` — `batchHashOf(items)`
- 하니스 3종 각각의 로컬 헬퍼 (`phase2.e2e.mjs`의 `batchHash()`, `phase2.live.mjs`의 인라인 `sha()`, `prepaid.e2e.js`의 `h()`)

**절대 금지**: canonical에 필드를 추가하는 것. `org`(소속)는 blob의 `items[]`에 선택 필드로 실려 음식점 앱까지 전달되지만 **해시에는 들어가지 않는다**(PROTOCOL.md §3, phase2.e2e.mjs §25가 회귀 단언).

**깨졌을 때**: 담당자 웹만 배포하면, **이미 설치된 모든 음식점 앱**이 복호화 후 재계산한 값과 어긋나 "명단 확인값 불일치"로 **수신을 전면 차단**한다. 사용자는 원인을 알 수 없고, 롤백 외에 복구 수단이 없다. 서버는 암호문을 못 열므로 중간에서 감지·보정할 수도 없다.

**부수 계약 — 충돌 사전 차단**: canonical에 `org`가 없으므로 *같은 음식점 · 같은 부서명 · 소속만 다른 · 명단 내용이 완전히 같은* 두 그룹은 `batch_hash`가 충돌한다. 담당자 웹이 **전송 전에** `collisionErrors()`로 막는다.
⚠️ 2026-09부터 서버의 멱등 키는 `batch_hash`가 아니라 `dedupe_key`이므로(C6), 두 그룹이 각자 다른 접수번호를 달면 서버에서는 **더 이상 조용히 사라지지 않는다**. 그래도 이 방어는 유지한다 — 음식점 앱은 `batch_hash`로 "이미 올린 명단"을 판정하므로, 충돌하는 두 건은 앱에서 서로를 중복으로 오인하게 만든다. 방어를 제거하면 사고 지점이 서버에서 사장님 화면으로 옮겨갈 뿐이다.

## C2. `district` 생성 규칙과 **정확 일치** 매칭

**계약**: `district = "{시도 전체명} {시군구명}"` — 3개 컴포넌트가 같은 규칙을 쓴다.
- 음식점 앱: `relayDistrict(addrHint)` = 시도명 + `' '` + 기관명에서 `'청'` 제거. 주소 우선순위는 `addrHint` → `meta.storeAddr`(LOCALDATA 공식 주소) → `meta.shopAddr` → `setupSelected.addr`.
- 담당자 웹: `jurisQuery()` = `sido=시도명`, `sigungu=기관명에서 '청' 제거`.
- 서버: `normalizeDistrict()`(NFC + 연속 공백 1칸 + trim)를 **저장·조회 양쪽에** 적용, 비교는 `=`.

**절대 금지 1 — 부분 일치로 되돌리는 것.** 과거 구현은 `district LIKE '{sido}%' AND district LIKE '%{sigungu}%'` 였다.
**깨졌을 때**: 시군구명이 다른 시군구명의 부분문자열인 **실제 3쌍** — **부산 서구⊂강서구, 대구 서구⊂달서구, 경기 양주시⊂남양주시** — 에서 남의 관할 음식점이 목록에 섞인다. 담당자가 **다른 구의 음식점에 직원 명단을 보내는** 개인정보 오배송 경로다. 회귀 단언: `harness/phase2.e2e.mjs` §20-h. 와일드카드 이스케이프(`%`·`_`·`\` + `ESCAPE '\'`)는 §20-j.

**절대 금지 2 — 클라이언트가 `district`를 안 보내게 만드는 것.**
**실제로 벌어진 일(2026-08-03)**: `relayDistrict()`가 검색으로 고른 가게의 공식 주소를 참조하지 못해(선택 결과의 `addr`을 저장하지 않았다) payload에서 필드가 통째로 생략됐고, **라이브 D1의 `district`가 전국 0건**이었다. 담당자 웹의 관할 목록이 항상 비어 있었지만 **verify-all은 9/9 통과**였다 — 서버 계약 테스트만 있었고 "클라이언트가 그 값을 실제로 만들어 보내는지"를 보는 테스트가 없었기 때문이다.
**현재 방어**: `meta.storeAddr` 저장(양 경로), 부팅 시 1회 자동 치유(`relayDistrictSyncSilent()` + `meta.districtSyncedAt` 도장), 그리고 **`harness/prepaid.e2e.js`가 실제 클라이언트의 `register-key` payload를 가로채 `district === '서울특별시 광진구'`를 단언**한다. 이 단언을 지우면 같은 장애가 조용히 재발한다.

`district`는 공개 사업장 정보이므로 zero-knowledge 불변식 위반이 아니다(PROTOCOL.md §4.6).

## C3. 백업 `schemaVersion` 정책

**계약**: `parseBackupPayload()`가 받아들이는 것은 ① `schemaVersion` 2 또는 3 + `payload.{employees,transactions}` ② 최상위 평면 `{employees, transactions}`(레거시 v1) 뿐. 그 외는 `throw '지원하지 않는 백업 형식'`.

**핵심**: **v2와 v3의 읽기 동작은 완전히 동일하다.** 필드 변환 코드가 없고, 없는 필드는 `norm()`이 기본값으로 채운다.

**규칙**
- 필드 **추가**만이라면 버전을 올리지 않는다(실제로 `org` 도입 때 3을 유지했다).
- 기존 필드의 **의미가 바뀌거나 제거될 때만** 올리고, **그때는 `parseBackupPayload()`에 변환 분기를 반드시 함께 넣는다.**

**깨졌을 때**: 버전만 올리고 변환을 안 넣으면 → 신버전 앱이 만든 백업을 구버전 앱이 `지원하지 않는 형식`으로 거부한다. 변환 없이 의미를 바꾸면 → **구 백업이 조용히 잘못 복원된다**(잔액이 틀린 채 열린다). checksum 불일치는 경고일 뿐 차단하지 않으므로 사용자가 그냥 진행한다.

관련: `backupCore()`의 **제외 목록**(`deviceSecret`·`privKeyWrapped`·`pinHash`·`pinFails`·`pinDelayUntil`)에서 `deviceSecret`을 빼면, 백업 파일 하나로 남의 전화번호가 복호화된다. 반대로 `privKeyWrapped`를 넣으면 백업 파일이 곧 개인키 유출이 된다. **이 목록은 보안 계약이다.**

## C4. 잠금 화면 allowlist (`LOCK_ALLOWED`)

**계약**: 잠금(=손님) 화면에서 실행 가능한 액션은 `index.html`의 `LOCK_ALLOWED` Set에 있는 18개뿐. 여기 없는 `data-a`는 `onClick` 진입부에서 통째로 차단된다.

> `//   ⚠️ 이 목록에 원장을 쓰는 액션을 추가하지 말 것. 손님은 '요청'만 만들 수 있고 '기록'은 만들 수 없다.`

4중 강제(액션 화이트리스트 / `onInput` 입력 id 화이트리스트 / 파일 input 3종 재방어 / 안드로이드 뒤로가기 차단) — 자세한 내용은 [08-frontend-conventions.md](08-frontend-conventions.md) §3.

**깨졌을 때**: 태블릿을 손님에게 넘긴 상태에서 손님이 장부를 수정·삭제·초기화하거나, 남의 백업 파일을 복원해 **장부를 통째로 탈취**할 수 있다. 실제로 적대 검증에서 치명 2건(3탭 전체 삭제 / 임의 백업 복원 탈취)이 배포 전에 잡혔고, 파일 input 3종을 스윕에 넣은 것도 그 결과다.

**유일한 예외**는 PIN 분실 복구 화면(진입 후 60초 카운트다운 게이트 + `allowLockedRestore` 1회성 플래그). 예외를 늘리지 말 것.

## C5. 요청(pending)의 휘발성

**계약**: 손님이 만든 요청(대상 직원·금액·서명)은 **`state` 메모리에만** 존재한다. IndexedDB·백업 JSON·서버 어디에도 쓰지 않는다. TTL **120초**(`TIMERS.pendingTtl`). 사장님이 PIN으로 열어 금액을 확인·수정하고 `saveUse()`로 저장해야만 원장 레코드가 생긴다 — **자동 저장 없음.**

회귀 단언: `prepaid.e2e.js` (10) "손님 화면 상태는 백업 파일에도 남지 않는다", (8-g0/g) TTL 119/121초 경계, (n) 중복 저장 없음.

**부속 규칙**
- 손님이 상세 화면을 왕복하면 **금액은 보존, 서명은 재작성**한다. 서명 dataURL의 사본을 어딘가에 두는 순간 이 불변식이 깨지므로 사본을 만들지 않는다(화면에도 명시).
- 사장님이 금액을 손님 요청과 다르게 고쳐 저장하면 **손님 서명을 자동 폐기**하고 재서명을 요구한다(분쟁 방어). 모든 요청 거래의 `note`에 `손님 요청 금액 N원`을 남긴다.
- `lock-to-pin`은 pending 요청도 함께 폐기한다(요청은 handoff 경로에서만 유효).

**깨졌을 때**:
- 요청을 영속화하면 → 손님이 **자기 손으로 장부를 쓴 것**이 되어 "손님은 요청, 사장님은 기록" 원칙이 무너지고, 서명 이미지(개인정보)가 승인 없이 기기·백업에 축적된다.
- 자동 저장을 넣으면 → 손님이 사장님 확인 없이 차감을 만들 수 있다.
- 금액 불일치 시 서명을 유지하면 → **손님이 서명하지 않은 금액에 손님 서명이 붙은 증표**가 생긴다(분쟁에서 그대로 무너지는 지점).

## C6. `/api/submit` 멱등 키 `dedupe_key`와 응답 `{deduped, status, repaired}`

**계약(2026-09 개정)**: 멱등 키는 `batch_hash`가 아니라 **`dedupe_key`** 다.
```
dedupe_key = submission_id ? 'sid:' + submission_id
                           : 'bh:' + batch_hash + '|' + year_month
UNIQUE(restaurant_id, dedupe_key)
```
- 재제출(같은 키): `200 {summary_id, deduped:true, status}` — 응답 형태는 **바뀌지 않았다**.
- **고아 요약 복구**: 기존 건이 `PENDING`이고 72시간 이내인데 암호문이 없으면 이번 요청의 암호문을 채워 넣고 `200 {summary_id, deduped:true, status:'PENDING', repaired:true}`. 처리·만료된 건(`APPROVED`/`REJECTED`/`EXPIRED`)이나 72시간이 지난 건에는 **절대** 새 암호문을 만들지 않는다 — 그것은 "수령 즉시 파기"를 되돌리는 경로다.
- 담당자 웹은 `deduped:true`이고 `status !== 'PENDING'`이면 "✅ 보냄"이 아니라 **"이미 있는 명단 · 상태 X"** 로 표시한다. `deduped` 필드가 없는 구서버 응답은 기존 동작(성공)으로 처리 — 하위 호환 유지.

**왜 바꿨나**: 옛 `UNIQUE(restaurant_id, batch_hash)`는 *같은 명단을 별도로 결제해 다시 보내는* 정상 업무를 **영구히** 삼켰다(달이 바뀌어도 막혔다). 게다가 담당자 화면에는 성공처럼 보였다. 이제 새 접수번호를 달면 같은 내용·같은 달이어도 새 건이 되고, **중복의 최종 판별자는 통장**이라는 앱 원칙대로 음식점 앱이 "이미 올린 명단과 같다" 경고로 판단 재료를 준다.

**깨졌을 때**
- `deduped`를 제거하면 → 이미 거절·만료된 명단을 다시 보낸 담당자가 "보냈다"고 믿는다.
- `dedupe_key`를 다시 `batch_hash`로 되돌리면 → 위의 "정상 업무가 삼켜지는" 사고가 그대로 돌아온다.
- `repaired` 분기의 조건(PENDING·72h·blob 없음) 중 **하나라도 느슨하게 하면** → 이미 파기된 명단의 암호문이 서버에 되살아난다(보존 정책 위반).

## C7. 서버 zero-knowledge 입력 검증 — `ciphertext` 4키 화이트리스트

**계약(2026-09 강화)**: `POST /api/submit`의 `blob.ciphertext`는 객체여야 하고, 키는 **`alg`(선택, 문자열 ≤64자)·`encKey`·`iv`·`ct`(필수, 비어 있지 않은 문자열, `^[A-Za-z0-9+/=]+$`) 넷뿐**이다.
- 그 밖의 키가 하나라도 있으면 `400 {error:'ciphertext 형식 오류(허용되지 않은 필드)'}`
- 필수 키가 없거나 모양이 어긋나면 `400 {error:'ciphertext 형식 오류(암호 blob 아님)'}`
- 저장은 **허용 4키만 재조립한 JSON**으로 한다 — 통과한 요청에도 다른 필드가 남지 않는다.

예전에는 "`ct`·`encKey`가 있는가"만 봤다. 즉 **추가 필드는 그대로 통과해 저장**됐다 — 담당자 웹 버그나 조작된 클라이언트가 `phone`·`name` 같은 평문 필드를 끼워 넣을 수 있는 자리였다.

명단 평문의 선택 필드(`org`·`payer`·`payMethod`)는 **암호문 안**에 있으므로 이 검사와 무관하다(서버는 존재조차 알지 못한다).

`verify-all.sh`의 체크 7이 라이브에서 이것을 직접 찌른다(평문 `items`를 보내 거부를 확인).

**깨졌을 때**: 클라이언트 버그·구버전이 평문 명단을 서버에 밀어 넣을 수 있고, 그 순간 **불변식 3(서버 평문 개인정보 미저장)이 D1에 물리적으로 깨진 상태**가 된다. 사후 삭제로도 "저장한 적 없다"는 개인정보처리방침 문구가 거짓이 된다.

주의: `verify-all.sh`는 한국어 문자열 `형식 오류`로 판정한다. **worker.js의 이 오류 문구를 바꾸면 진짜 통과가 거짓 실패가 된다** — 문구 변경 시 하니스도 함께 고칠 것.

## C8. 담당자 이메일 허용 도메인 (양쪽 동시 변경)

**계약**: 서버 `AGENCY_EMAIL_DOMAIN_RE = /^([a-z0-9-]+\.)*(go|korea|or|ac)\.kr$/` (worker.js `isAgencyEmail`)와 담당자 웹 `AGENCY_EMAIL_RE`(로컬파트 검사만 덧댄 **동일 규칙**)는 반드시 함께 바뀌어야 한다.

**깨졌을 때**: 클라이언트만 넓히면 사용자가 통과한 줄 알고 진행하다 서버 `400 invalid_domain`으로 막힌다. 서버만 넓히면 정당한 담당자가 클라이언트 단계에서 거부된다. 라벨 경계(`([a-z0-9-]+\.)*`)를 풀면 `evilgo.kr`·`go.kr.attacker.com`이 통과한다.

## C9. 접수번호(`submission_id`) 발급 규칙 — **담당자 웹 쪽 계약**

**계약**: 담당자 웹은 서버 전송 그룹(음식점 × 부서)마다 **[보내기] 클릭 1회당 새 `submission_id`(UUID v4)** 를 만들고 `body.summary.submission_id`로 보낸다.
- **[실패 재시도]는 같은 sid를 다시 쓴다**(`relayResults` 행에 보관). `fetchRetry`의 자동 재시도도 같은 body라 자연히 같은 sid다.
- 새로 [보내기]를 누르면 새 sid다.
- 서버 형식: 8~64자 `[A-Za-z0-9-]`. 어긋나면 `400 {error:'submission_id 형식 오류'}` — **조용히 무시하지 않는다**(무시하면 "새 번호로 보냈다"고 믿은 재전송이 멱등으로 삼켜진다).

**깨졌을 때**
- 재시도가 **새 sid**를 만들면 → 네트워크가 끊겼다 붙은 한 번의 전송이 **두 건**이 되어 선금이 두 배로 들어간다. 이것이 C9가 존재하는 유일한 이유다.
- 새 [보내기]가 **같은 sid**를 재사용하면 → C6 이전의 사고(정상 재전송이 삼켜짐)가 그대로 돌아온다.
- 담당자 웹이 sid를 아예 안 보내면 → 구버전 취급(`bh:` 키)이 되어 같은 달 같은 내용은 다시 못 보낸다.

**⚠️ 이 계약을 지키는 테스트는 없다** — 담당자 웹은 브라우저로 구동되는 하니스가 없다([06](06-testing.md) G1). 코드를 고칠 때 사람이 확인해야 한다.

## C10. 직접 전달 파일·QR의 `transfer_id`

**계약**: 담당자 웹이 직접 전달(무보관 모드) JSON을 만들 때 `transfer_id`(UUID v4)를 넣고, **파일과 QR은 같은 JSON을 쓰므로 같은 값**을 갖는다. 음식점 앱은 처리한 id를 `meta.receivedTransferLog`에 남기고, 같은 id를 다시 만나면 **묻지 않고 막는다**(alert 후 종료).

`transfer_id`는 `batch_hash` canonical과 **무관**하다(C1). 값이 없는 구버전 파일은 기존 흐름(같은 명단 해시 경고 → 사장님 판단)으로 처리된다.

**왜 경고가 아니라 차단인가**: `batch_hash`는 "같은 이름·금액"이면 달이 달라도 같다. 그래서 그것만으로는 *같은 파일을 두 번 열었다* 와 *같은 내용의 새 결제* 를 구분할 수 없어 경고까지가 한계였다. `transfer_id`는 **파일 한 장**을 가리키므로 "두 번 올렸다"가 확실하다. 새로 결제받은 명단이면 담당자가 새 파일을 만들어 주면 된다(그 파일은 id가 다르다).

**깨졌을 때**: 앱이 id 기록을 빼먹으면(또는 `receivedTransferLog`가 백업에서 누락되면) 카톡으로 받은 같은 파일을 두 번 열어 **선금이 두 배**로 들어간다. 파일·QR이 서로 **다른** id를 갖게 만들면 "파일로 올린 뒤 QR로 또 올리는" 경로가 열린다.

## C11. 승인 아웃박스 — **장부에 반영한 신청은 다시 반영하지 않는다**

**현장 결함(이 계약이 생긴 이유)**: 승인은 ① 명단을 장부에 넣고 ② 서버에 "처리 완료"를 알리는 **두 걸음**인데, ②가 실패해도(끊긴 와이파이·서버 5xx) 앱은 그 항목을 수신함에서 지우고 넘어갔다. 그 신청은 다음 수신함 조회에서 `PENDING`으로 되살아나고, 사장님이 다시 승인하면 **같은 명단이 장부에 두 번** 들어간다.

**계약**
1. 장부에 반영하는 순간 `summary_id`를 `meta.approvedSummaryLog`에 남긴다 — **장부(직원·거래)와 같은 `repo.apply()` 한 번**으로. 둘로 나누면 그 사이의 중단이 곧 이중 반영 경로다.
2. `relayApprove(sid)` 진입 시 sid가 `approvedSummaryLog`에 있으면 **복호화·검토창·장부 반영 없이 통보만** 재시도한다.
3. 통보 성공 판정은 `r.ok || 409 || 404`. 셋 다 "서버 쪽에 더 할 일이 없다"는 뜻이라 대기열에서 뺀다. 그 밖의 상태·throw면 `pendingNotify`에 남긴다.
4. 미통보 항목은 수신함에서 **[열어보기·승인]/[거절] 버튼을 주지 않고** `✅ 장부에 반영됨 · 서버 알림 대기` + [서버에 다시 알리기]만 보여준다.
5. `flushPendingNotify()`는 부팅·`online` 이벤트·수신함 열기 직전·PIN 해제 직후에 돈다. **잠금(손님) 화면에서는 절대 돌지 않는다** — 통보는 소유 증명(개인키 복호)이 필요한데 "손님 화면의 어떤 경로도 개인키를 쓰지 않는다"가 구조적 약속이다(C4).
6. 거절(`relayReject`)도 같은 판정을 쓴다. 예전에는 응답을 보지 않고 항목을 지웠다 — 서버가 못 받았는데 화면에서는 사라지니 사장님은 처리됐다고 믿고, 그 신청은 다음 조회에서 되살아난다.

**통보 실패는 장부를 되돌리지 않는다.** 장부가 진실이고 서버는 중계일 뿐이다(불변식 5).

**깨졌을 때**: 어느 한 조각만 빠져도 선금이 두 배가 된다. 특히 **1의 "한 번의 apply"** 를 둘로 나누는 리팩터링이 가장 조용한 회귀다.

## C12. 등록 해제 = 30일 휴지통 — **서버 상수와 앱 문구가 같은 숫자를 말한다**

**계약**: `POST /api/deregister`는 행을 지우지 않고 `public_key_registry.deregistered_at`에 시각을 적는다. 서버 상수 **`DEREGISTER_GRACE_MS = 30일`**, 응답은 `{ok:true, backup_kept_until:<epoch ms>}`.
- 담당자에게는 **즉시** '없는 가게': `/api/public-key` 404, `/api/registered`·`/api/registered-list` 제외, `/api/agency/keycheck` 404, `/api/contact` 404, `/api/admin/stats`의 `restaurants.current` 제외.
- **해제 중에도 되는 것**: `/api/challenge`(소유 증명 발급)와 `/api/ledger-backup/get`(백업 되찾기). ← 이 변경의 목적 자체다.
- **막는 것**: `/api/ledger-backup` POST → `409 {error:'deregistered'}`.
- 같은 공개키로 `register-key` → `200 {ok:true, reactivated:true}`(인증 불요 — 같은 열쇠 = 같은 기기). 다른 공개키면 선착순 신규 등록이고 **새 열쇠로는 열 수도 없는 옛 백업·옛 연락처는 그 시점에 삭제**한다.
- cron이 `deregistered_at < now-30일`인 행의 `ledger_backup`을 **먼저** 지우고 키 행을 지운다(순서 중요 — 키 행이 먼저 사라지면 남은 백업은 아무도 되찾을 수 없는 죽은 데이터가 된다).

**앱 쪽 짝**: `relayStop()`의 확인창이 `· 서버에 보관된 잠긴 장부 백업은 30일 뒤 삭제돼요(그 안에 다시 등록하면 되찾을 수 있어요).`라고 말한다.
🔴 **서버 상수를 바꾸면 이 문구도 함께 바꿔야 한다.** 코드가 대조하지 않으므로 어긋나도 아무도 실패하지 않는다 — 사장님만 틀린 날짜를 믿는다.

**왜 즉시 삭제를 그만뒀나**: 공개키가 사라지면 소유 증명을 더는 발급받을 수 없으므로 **백업을 되찾을 길도 함께 닫힌다.** 기기를 잃은 사장님이 "일단 명단 받기를 중단해 두자"고 누르는 순간, 남아 있던 복구 수단까지 잃는 구조였다.

**깨졌을 때**: 휴지통을 즉시 삭제로 되돌리면 위 사고가 돌아온다. 반대로 **활성 필터(`deregistered_at IS NULL`)를 한 곳이라도 빠뜨리면** 해제한 가게에 담당자가 계속 명단을 보낸다(받을 사람이 없는 개인정보 전송).

## C13. 잠긴 백업 파일 포맷 `prepaid-locked-backup`

**계약**: PIN 분실 복구 화면의 초기화(`pinReset`)가 만드는 최종 백업은 **공개키로 잠근 파일**이다. 포맷과 복원 규칙은 [03-data-model.md](03-data-model.md) §4 참조.
- `confirmWipeWithBackup(intro, {locked:true})` — **`locked`는 pinReset 경로에만** 붙인다. 설정의 인증된 전체 초기화는 지금도 평문 백업이다(PIN을 통과한 사장님 본인이므로).
- locked 경로는 **`markBackupSaved()`를 부르지 않는다**(`meta.lastBackupAt` 불변).
- 복원 파일 선택기는 `type`으로 3갈래다: `prepaid-key-backup`(열쇠) / `prepaid-locked-backup`(잠긴 백업) / 그 외(평소 백업).

**왜**: 이 화면은 비밀번호를 모르는 사람도 누를 수 있어야 한다(그래야 잠긴 기기를 되살린다). 그런데 그 경로가 **직원 이름·금액이 평문으로 든 백업**을 폰 다운로드 폴더에 떨궜다 — 가게에 놓인 태블릿을 잠깐 만진 사람이 [초기화]만 눌러 장부를 통째로 가져갈 수 있었다.

**함께 지켜야 하는 기존 계약**: `pinReset`은 **절대 `/api/deregister`를 부르지 않는다**(무PIN 화면이라 제3자 초기화 → 선착순 재등록으로 가게를 가로채는 경로가 된다). 복구 화면의 파괴 버튼은 진입 후 **60초 카운트다운** 뒤에만 활성된다. 둘 다 `prepaid.e2e.js`가 정적 계약으로 고정하고 있다.

**깨졌을 때**: `locked` 플래그를 설정 초기화까지 확대하면 사장님이 평소 쓰던 평문 백업이 사라져 **다른 기기로 이사할 수 없게 된다**(잠긴 파일은 열쇠가 있는 기기에서만 열린다). 반대로 pinReset에서 빼면 위의 장부 탈취 경로가 돌아온다.

## C14. `register-key` 재등록의 `auth_token`과 `district` 권한 경계

**계약(서버)**: 같은 공개키로 다시 등록할 때 **저장된 `district`가 비어 있지 않고 값이 다르면** 소유 증명이 필요하다(실패 `401 auth_required`). 저장값이 NULL/빈 문자열이면 지금처럼 무인증 갱신(레거시 치유 목적 유지). 비교는 `normalizeDistrict()`.

**계약(앱)**: `relayRegister()`는 **이미 등록된 기기**(`relayRegistered() && meta.relayRegisteredAt > 0`)일 때 `payload.auth_token`을 함께 싣는다. 토큰을 못 얻으면(서버에 다른 열쇠가 등록돼 챌린지를 못 푸는 경우 등) 예전처럼 토큰 없이 보내고, 401이면 기존 안내(`REGISTER_TAKEN_MSG`)로 간다 — **막다른 길을 만들지 않는다.**

**왜**: `restaurant_id`도 공개키도 공개값이다. 인증이 없으면 그 둘만 아는 제3자가 '같은 키 재등록'만으로 **남의 가게 관할을 바꿔** 담당자 목록에서 사라지게 할 수 있었다.

**깨졌을 때**: 앱이 토큰을 안 실으면 → 관할이 바뀐 **자기 가게**를 다시 등록할 때 401을 받고 "이미 등록되어 있어요"로 오안내한다(사장님은 자기 가게인데 막힌다). 서버가 인증을 안 걸면 → 위의 관할 탈취 경로가 열린다. 회귀 단언은 `prepaid.e2e.js`(앱이 실제로 토큰을 싣는가)와 `phase2.e2e.mjs` §39(서버가 저장값 유무로 갈라 판정하는가) **양쪽에** 있다.

## 부록 — 계약을 바꿔야 할 때의 배포 순서

```
① D1 마이그레이션 → ② 서버(wrangler deploy) → ③ 프론트
```
③의 내부 순서는 **"새 필드를 읽는 쪽을 먼저"** 가 원칙이다(수신자가 받을 수 있게 된 뒤에 발신을 바꾼다). 양쪽 새 필드가 전부 **선택 필드**라 구버전이 무시해도 안전한 릴리스라면 순서는 자유다.

**beta.48 실제 순서** — `server/migrations-2026-09.sql` 머리말·`PROTOCOL.md` §9 기준:
```
마이그레이션 7문 → 서버 deploy → 담당자 웹(pages deploy) → 음식점 앱(git push)
```
서버를 먼저 배포하면 신규 제출이 `dedupe_key` 컬럼 부재로 실패한다. 반대로 프론트를 먼저 내도 `submission_id`·`transfer_id`는 둘 다 선택 필드라 구버전 서버·구버전 앱이 무시할 뿐 깨지지 않는다.
