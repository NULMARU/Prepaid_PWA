# 05 — 절대 불변식과 강제 지점

**원문은 `CLAUDE.md`의 「절대 불변식」 6개다.** 이 문서는 그 6개가 **코드 어디서 강제되는지**와 **어겼을 때의 규제·신뢰 리스크**를 붙인다.

> 이 6개는 기능 요구가 아니라 **사업 존립 조건**이다. 하나라도 깨지면 서비스의 법적 성격이 바뀌거나(1·2·5), 개인정보 사고가 되거나(3·4), 운영을 지속할 수 없게 된다(6).

---

## I1. 운영자는 자금을 수수·보관·이체·정산하지 않는다 (결제 기능 금지)

| 어디서 강제되나 | 방식 |
|---|---|
| 전 코드베이스 | **결제·계좌·이체 코드가 존재하지 않는다**(부재로 강제). 서버에 금액은 `deposit_summary.total_amount`(부서별 합계, 표시·통계용)와 `stats_counter.amount_total`(누적 카운터)만 있다 |
| `docs/terms.html` / `docs/TERMS.md` 1항 | "운영자는 자금을 수수·보관·이체·정산하지 않으며 결제 기능을 제공하지 않습니다. 선금은 기관과 음식점 간의 직접 거래입니다" |
| 사용자 문구 | 앱·담당자 웹·홈페이지에 "돈은 계좌 이체" 오해 차단 문구 배치. 용어 체계에서 "구청/기관 선금 받기" 계열을 전면 폐기한 것도 같은 이유 |

**리스크**: 결제·정산이 들어오는 순간 전자금융거래법상 **선불전자지급수단 발행업/전자지급결제대행** 영역으로 이동한다. 등록·자본금·이용자자금 별도관리 의무가 생기고, 무료 운영이 불가능해진다.

**주의할 유혹**: "잔액 충전 버튼", "정산 리포트", "미수금 자동 청구" 같은 요청은 전부 이 선을 넘는다.

## I2. 선금 기록은 해당 음식점 1곳에서만 유효 (다점포 통용 잔액 금지)

| 어디서 강제되나 | 방식 |
|---|---|
| `index.html` — IndexedDB `prepaid-ledger-db` | 원장이 **그 기기 안에만** 존재. 다른 음식점의 원장을 읽는 코드 경로가 없다 |
| `server/schema.sql` | 잔액 컬럼이 **없다**. 서버는 부서·음식점별 `total_amount`만 알고 개인별 금액을 모른다 |
| 서버 API 표면 | 잔액 조회·차감 엔드포인트가 존재하지 않는다(`server/PROTOCOL.md` §4 전체) |
| 직원용 앱 | **별도 리포·미연동**. 안내서 `docs/manual-staff.html` 최상단이 "공식 잔액은 음식점 장부가 기준"임을 경고 |
| `agency-web/index.html` | 제출 단위가 `(음식점, 부서)` 그룹이며 음식점을 가로지르는 잔액 개념이 없다 |

**리스크**: 여러 가맹점에서 통용되는 잔액은 그 자체로 **선불전자지급수단**의 정의에 들어간다(2개 이상 업종/가맹점 사용). 규제 지위가 바뀌고 I1과 함께 무너진다.

**주의할 유혹**: "직원용 앱에서 잔액을 실시간 동기화", "여러 단골집 잔액 한눈에" — 둘 다 이 불변식을 깨는 요청이다.

## I3. 서버는 평문 개인정보를 저장하지 않는다 (zero-knowledge)

| 어디서 강제되나 | 방식 |
|---|---|
| `server/src/worker.js` — `/api/submit` 핸들러 | `typeof blob.ciphertext !== 'object' \|\| !ct \|\| !encKey` → `400 'ciphertext 형식 오류(암호 blob 아님)'` |
| `server/schema.sql` | 평문 개인정보 컬럼 자체가 없다. `deposit_summary`는 총액·인원수·해시만 |
| `worker.js` — `sha256hex()`, `normalizeEmailHash()`, `isEmailHash()` | 담당자 이메일은 `agency_otp`·`agency_token`·`consent_log` 어디에도 평문으로 들어가지 않는다(SHA-256 64자 hex). 구버전이 남긴 평문 행이 오면 **하위 저장소로 흘러가기 전에 해싱**한다 |
| `worker.js` — 로깅 정책 | OTP 발송 실패 시 `reason`만 로깅, 이메일·OTP 평문은 로깅하지 않음. 집계(`bumpStats`)도 조직정보·공개ID·카운터만 |
| 암호화 위치 | 명단은 **담당자 브라우저**에서 RSA-OAEP+AES-GCM으로 봉인된다(`agency-web` `encryptBlob()`). 서버는 복호화 키를 갖지 않는다 |
| 하니스 | `phase2.e2e.mjs` §4 "서버는 개인정보 평문 미저장 확인", §15b "저장소에 평문 이메일 부재"; `verify-all.sh` 체크 7이 **라이브**에서 평문 제출 거부를 확인 |

**리스크**: 개인정보처리방침(`docs/privacy.html`, 시행 2026-07-06)이 "운영자는 복호화할 수 없습니다", "해시값(평문 미보관)"이라고 명시한다. 이것이 거짓이 되는 순간 **방침 위반 + 개인정보보호법 문제 + 신뢰 붕괴**가 동시에 온다. 사후 삭제로 회복되지 않는다.

**허용되는 예외(오해 방지)**: `public_key_registry.district`(관할 지역)와 `restaurant_name`은 **공개 사업장 정보**라 평문 저장이 허용된다(PROTOCOL.md §0·§4.6). 개인정보가 아니다.

## I4. 전화번호는 어떤 서버 경로에도 실리지 않는다

| 어디서 강제되나 | 방식 |
|---|---|
| `agency-web/index.html` | 전화번호 입력·CSV 열·전송 필드가 **존재하지 않는다**. blob `items[]`는 `{name, dept, amount, org?}` |
| `server/schema.sql` / `worker.js` | 전화번호 컬럼·필드 없음 |
| `index.html` — `setPhone()` / `getPhone()` | 기기 로컬 저장 시 `aesEncryptStr(…, meta.deviceSecret)` = **PBKDF2-SHA256 120,000회 → AES-GCM-256**. `meta.deviceSecret`은 백업에서 제외되므로 다른 기기로는 복호화 불가 |
| `index.html` — **`stripPhonesForCloud()`** | 클라우드 원장 백업 blob 생성 시 모든 직원에서 `phone`·`phoneConsent`를 **구조분해로 제거**. 암호문조차 서버로 가지 않는다 |
| `index.html` — `setPhoneConsent()` + UI | 직원 동의가 있을 때만 저장. "전화번호는 이 폰에만 저장되며 서버로 전송되지 않아요" 고지. 「전화번호 일괄 파기」 기능 제공 |

**리스크**: 전화번호는 그 자체로 식별성이 강하고, 문자 발송 기능과 결합하면 **연락처 DB**가 된다. 이 하나 때문에 서비스 전체가 "개인정보를 모으는 서비스"로 재분류된다.

**가장 깨지기 쉬운 지점**: `stripPhonesForCloud()`. 클라우드 백업에 필드를 추가하다가 이 필터를 우회하면 **암호문 형태로라도 전화번호가 서버에 올라간다**. 신규 필드를 넣을 때 반드시 이 함수를 지나는지 확인할 것.

## I5. 원장의 진실은 음식점 기기다

| 어디서 강제되나 | 방식 |
|---|---|
| `index.html` — `derive()` / `balanceOf()` | 잔액은 **로컬 거래의 파생값**. 서버에서 잔액을 받아오는 경로가 없다 |
| `index.html` — 해시 체인 `txHashOf()` / `verifyChain()` / `chainTip()` | 원장 무결성을 기기가 스스로 증명한다 |
| `worker.js` — `ledger_backup` | 저장은 **클라이언트 자체 공개키로 암호화된 blob 1행**뿐. 서버는 내용을 모르고, 읽기도 소유증명(`auth_token`)이 필요하며, 사용자가 `/api/ledger-backup/delete`로 언제든 지운다 |
| 「직접 전달」 모드 | 서버를 아예 경유하지 않는 전달 경로가 상시 존재 — 서버가 죽어도 서비스가 성립한다 |

**리스크**: 서버가 잔액의 원본이 되면 I1·I2가 동시에 흔들리고(=자금 보관자처럼 보인다), 서버 장애가 곧 영업 중단이 된다. 또한 zero-knowledge 주장이 무너진다.

**주의할 유혹**: "기기를 잃어버렸을 때를 위해 서버가 잔액을 알고 있게 하자" — 이미 **암호화 백업**으로 해결한 문제다. 평문화하지 말 것.

## I6. 완전 무료 운영 (광고·유료 기능 금지, Cloudflare 무료 플랜 유지)

| 어디서 강제되나 | 방식 |
|---|---|
| 전 코드베이스 | 광고 스크립트·결제·구독 코드 없음. 외부 스크립트 의존이 없다(단일 파일 정책) |
| `server/wrangler.toml` | Workers 무료 플랜 범위 구성. **Cloudflare Email Sending(유료 플랜 필요) 대신 Resend 무료**를 쓰는 이유가 주석에 명시돼 있다 |
| `worker.js` — 레이트리밋 5종 | 전역 60/분, `public-key` 20/분, `registered-list` 20/분, `admin/stats` 10/분, `feedback` 5/분 — 무료 한도 안에서 버티기 위한 장치이기도 하다 |
| `worker.js` — TTL 상수 + cron | 저장을 늘리지 않는다(암호문 즉시 파기, 요약 30일, consent·feedback 180일) |
| `docs/terms.html` 1항 | "무료로 제공되는 장부 기록 도구" |

**먼저 막히는 한도(비용 문서 결론)**: ① **Resend 무료 하루 100통**(담당자 OTP) → ② data.go.kr 일일 한도 → ③ D1 저장 5GB. 무료 연장 레버 1순위는 **담당자 세션 유효기간 연장**(현재 24시간 토큰 + `sessionStorage` 보존으로 새로고침마다 OTP를 소모하지 않게 이미 적용).

**리스크**: 유료화·광고는 이 서비스의 신뢰 포지션(공공기관 담당자가 쓰는 무료 공익 도구)을 직접 훼손한다. 유료 플랜 전환은 운영 지속성 판단을 통째로 바꾸므로 **오너 결정 사항**이다.
